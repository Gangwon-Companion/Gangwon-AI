# PostgreSQL RDB 검색 성능 측정 결과

측정일: 2026-08-21

## 테스트 목적과 측정 범위

이 테스트는 사용자의 자연어를 앞단 노드가 파싱한 뒤 생성하는 `SearchRequest`를
RDB 검색엔진에 전달했을 때, 후보 목록을 반환하는 데 걸리는 시간을 측정한다.

```text
사용자 입력
  → Input Parser / Agent에서 지역·검색어·필수조건·Geo 추출
  → SearchRequest 생성
  → [측정 시작] RdbPlaceSearchEngine.search()
  → JPA 동적 조건 생성
  → PostgreSQL 조회
  → 거리·선호 점수 계산 및 정렬
  → SearchResponse 생성
  → [측정 종료]
```

자연어 파싱, LangGraph 노드 실행, AI와 BE 사이의 HTTP 왕복은 포함하지 않았다.
따라서 이 결과는 사용자 요청 전체 응답시간이 아니라 **검색 요청이 완성된 이후의
RDB 검색엔진 처리시간**이다.

## 결론

현재 RDB 검색은 도메인당 5,000행과 단일 요청에서 p95 15ms 이내다. 동시성
50에서는 키워드 검색 p95가 200~256ms, 결과가 없는 LIKE 검색 p95가 313ms까지
증가했다. 오류는 전체 측정에서 0건이었다.

선행 와일드카드(`%term%`) 키워드 검색은 PostgreSQL 실행계획에서 Seq Scan을
사용했다. 도메인당 행 수가 1,000에서 5,000으로 5배 증가할 때 음식점 키워드의
DB 실행시간은 1.436ms에서 4.368ms, 희소 숙소 검색은 1.037ms에서 6.081ms로
증가했다. 현재 규모에서는 사용 가능하지만 데이터와 동시 요청 증가에 선형에 가까운
비용 증가가 예상된다.

## 테스트 구성

- 데이터: Restaurant/Lodging 각각 1,000행과 5,000행
- 검색 시나리오: 6개
- 사전 실행: 실행별 100건
- 본 측정: 시나리오·동시성별 300건
- 동시성: 1, 10, 50
- 반복: 데이터 규모별 3회

측정값은 각 반복에서 얻은 percentile을 다시 3회 산술평균했다. 서로 다른 반복의
개별 요청 시간을 하나로 합쳐 percentile을 다시 계산하지 않았다. 공식 본 측정은
총 `6개 시나리오 × 3개 동시성 × 300건 × 3회 × 2개 데이터 규모 = 32,400건`이며,
모든 요청의 오류 수를 합산했다.

### 테스트 데이터 구성

테스트에는 같은 결과를 반복해서 확인할 수 있도록 규칙이 고정된 합성 데이터를 사용했다.
실행마다 Restaurant/Lodging 데이터를 같은 규칙으로 재생성했다.

- Restaurant: 절반은 `강릉 한식당`, 절반은 `강릉 카페`
- Lodging: 절반은 `강릉 바다 숙소`, 절반은 `강릉 시내 호텔`
- 모든 행의 지역은 `강릉`
- 좌표는 강릉 중심점 주변의 고정 공식으로 생성
- 데이터 규모는 도메인별 1,000행과 5,000행
- 응답 `limit`은 10건

이 구성은 같은 입력에서 같은 후보 수와 검색 계획을 재현하기 위한 것이다. 실제 데이터의
단어 분포, 중복도, 결측률을 재현하기 위한 데이터는 아니다.

### 검색 시나리오

| ID | 앞단에서 전달됐다고 가정한 값 | 검증 목적 |
|---|---|---|
| `restaurant-region` | `domain=RESTAURANT`, `region=GANGNEUNG` | 단순 지역 필터 |
| `restaurant-keyword` | 지역 + `query_text=한식` | `%LIKE%` 키워드 검색 |
| `restaurant-multi-filter` | 지역 + `카페` + 반려동물·크기·휠체어 조건 | 다중 조건과 근거 부족 처리 |
| `restaurant-geo` | 지역 + 중심좌표 `37.75, 128.90` + 반경 2km | bounding box와 실제 거리 계산 |
| `lodging-keyword` | 지역 + `query_text=바다` | 설명을 포함한 키워드 검색 |
| `lodging-sparse` | 지역 + 존재하지 않는 검색어 | 결과 0건일 때 전체 탐색 비용 |

키워드 조건은 현재 구현과 동일하게 `lower(field) LIKE '%term%'` 형태다. 일반 B-tree
인덱스가 선행 와일드카드 검색을 가속하지 못하는 상태를 그대로 측정했다. 반려동물과
휠체어 원본이 없는 Restaurant/Lodging은 탈락시키지 않고 `INSUFFICIENT_EVIDENCE`로
반환하는 현재 계약을 유지했다.

### 부하 생성 방식

- 각 실행의 본 측정 전에 6개 시나리오를 순환하며 100건 warm-up
- 동시성별 고정 크기 스레드 풀 사용
- 동시성 1, 10, 50을 순서대로 측정
- 각 시나리오와 동시성 조합마다 요청 300건 실행
- 요청별 `System.nanoTime()`으로 엔진 호출 전후를 측정
- 전체 wall-clock 시간으로 초당 처리량 계산
- 반환 후보 수와 예외 발생 수를 함께 기록
- PostgreSQL 쿼리 시간은 동일 데이터에서 별도로 `EXPLAIN (ANALYZE, BUFFERS)` 실행

동시성 50에서는 DB 연결 대기와 애플리케이션 스레드 경합도 측정시간에 포함된다.

모든 조합의 원본은 JSON 결과 파일에 보관했다.

## 실행계획

- 지역 검색: 기본키 Index Scan, 1,000행 0.143ms / 5,000행 0.152ms
- 음식점 키워드: Seq Scan, 1,000행 1.436ms / 5,000행 4.368ms
- Geo bounding box: 기본키 Index Scan, 1,000행 0.060ms / 5,000행 0.086ms
- 결과 없는 숙소 LIKE: Seq Scan, 1,000행 1.037ms / 5,000행 6.081ms

원본은 `performance/results/`, 실행계획은 `performance/plans/`에 있다.

## 결과 해석

- 단일 요청에서는 5,000행에서도 모든 대표 시나리오의 p95가 15ms 이하였다.
- 음식점 키워드의 단일 요청 p95는 1,000행 8.27ms에서 5,000행 13.89ms로 약 68% 증가했다.
- 동시성 50의 음식점 키워드 p95는 140.31ms에서 256.24ms로 약 83% 증가했다.
- 동시성 50의 희소 검색 p95는 183.48ms에서 313.10ms로 약 71% 증가했다.
- 5,000행·동시성 50에서 가장 높은 p99는 희소 검색의 443.74ms였다.
- Geo 검색의 DB 실행시간은 5,000행에서도 0.086ms로 이번 데이터 범위에서는 안정적이었다.
- 키워드와 희소 검색은 Seq Scan을 사용했으며 행 수 증가에 따라 DB 실행시간도 증가했다.
- 공식 측정 32,400건에서 검색 예외는 0건이었다.

현재 데이터 규모에서는 사용 가능한 속도지만, 선행 와일드카드 LIKE 검색은 데이터가
커질수록 전체 스캔 비용이 증가한다. 이후 Elasticsearch를 같은 시나리오로 측정하여
속도뿐 아니라 검색 결과의 유연성과 관련도도 함께 비교해야 한다.

## 해석 제한

- 엔진 메서드부터 후보 반환까지 측정했으며 자연어 파싱과 HTTP 왕복은 제외했다.
- 합성 데이터이므로 실제 데이터 분포와 한국어 의미 검색 품질을 대표하지 않는다.
- 검색 품질 기준 규칙은 고정했지만 사람 판정 기반 Precision/Recall/NDCG는 Phase 4의
  Elasticsearch 결과와 비교하기 전에 별도로 산출해야 한다.
- 현재 결과는 인덱스가 없는 LIKE 검색 측정값이다. `pg_trgm` 적용 결과와 혼합하지 않는다.
