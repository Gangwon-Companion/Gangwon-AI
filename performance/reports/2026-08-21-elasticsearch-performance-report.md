# Elasticsearch 검색 성능 측정 결과

측정일: 2026-08-21

## 측정 목적과 범위

사용자 입력을 앞 단계에서 해석해 만든 `SearchRequest`가 검색 엔진에 전달된 시점부터 검색 결과가 반환될 때까지를 측정했다.

```text
사용자 입력
  → 앞 단계에서 지역·검색어·필수조건·좌표 추출
  → SearchRequest 생성
  → [측정 시작] ElasticsearchPlaceSearchEngine.search()
  → Elasticsearch BM25 검색과 필터 적용
  → 거리·선호 점수 계산과 정렬
  → SearchResponse 생성
  → [측정 종료]
```

자연어 분석, AI와 BE 사이의 HTTP 왕복, 화면 렌더링 시간은 포함하지 않는다. 따라서 이 결과는 전체 사용자 응답 시간이 아니라 **파싱된 검색 조건을 전달한 이후의 검색 엔진 처리 시간**이다.

## 결론

Restaurant와 Lodging 각각 5,000건인 조건에서 단일 요청의 검색 시나리오 p95는 2.75~6.71ms, 동시 요청 50의 p95는 24.65~81.43ms였다. 전체 32,400건의 측정 요청에서 오류는 0건이었다.

동일 조건의 기존 RDB 검색과 비교하면 5,000건·동시 요청 50에서 Elasticsearch의 p95는 일반 시나리오 기준 61.4~72.3% 감소했다. 특히 검색 결과가 없는 숙소 검색은 339.34ms에서 24.65ms로 92.7% 감소했다. 1,000건·동시 요청 10의 단순 지역 필터처럼 일부 조합에서는 RDB보다 느렸지만, 키워드 검색과 데이터 증가 및 높은 동시성 조건에서는 Elasticsearch의 개선 폭이 컸다.

현재 규모에서는 두 방식 모두 사용 가능한 속도지만, 키워드 검색의 유연성과 동시 요청 증가를 고려하면 Elasticsearch 전환 효과가 확인됐다.

## 측정 조건

- 데이터: Restaurant와 Lodging 각각 1,000건, 5,000건
- 검색 시나리오: 6개
- 응답 제한: 상위 10건
- 워밍업: 실행별 100건
- 본 측정: 시나리오·동시성 조합별 300건
- 동시 요청: 1, 10, 50
- 반복: 데이터 규모별 3회
- 대표값: 각 회차에서 계산된 p50·p95·p99·처리량의 3회 중앙값
- 오류 판정: 검색 호출 중 예외가 발생한 요청

공식 측정 요청 수는 `6개 시나리오 × 3개 동시성 × 300건 × 3회 × 2개 데이터 규모 = 32,400건`이다. 워밍업 요청은 결과 집계에서 제외했다.

각 실행은 동일 규칙으로 데이터를 다시 생성하고 색인을 새로 구성했다. 검색 결과는 일반 시나리오에서 10건, 희소 검색 시나리오에서 0건인지 함께 검사했다.

## 검색 시나리오

| ID | 전달 조건 | 확인 목적 |
|---|---|---|
| `restaurant-region` | 음식점, 강릉 | 단순 지역 필터 |
| `restaurant-keyword` | 음식점, 강릉, `한식` | 한글 키워드 검색 |
| `restaurant-multi-filter` | 음식점, 강릉, `카페`, 반려동물 관련 조건 | 키워드와 복합 필터 |
| `restaurant-geo` | 음식점, 강릉, 중심 좌표, 반경 2km | 위치 필터와 거리 점수 |
| `lodging-keyword` | 숙소, 강릉, `바다` | 한글 키워드 검색 |
| `lodging-sparse` | 숙소, 강릉, 존재하지 않는 검색어 | 결과가 없는 검색 비용 |

거리 조건은 외부 지도 API가 아닌 위도·경도를 이용한 직선거리 계산이다. 따라서 도로 이동시간이나 실제 이동경로의 성능은 이번 측정 대상이 아니다.

## 기존 RDB 결과와 비교

5,000건·동시 요청 50 조건의 3회 중앙값 비교다. 음수 변화율은 Elasticsearch의 응답 시간이 감소한 것을 의미한다.

| 시나리오 | RDB p95 | Elasticsearch p95 | p95 변화 | 처리량 변화 |
|---|---:|---:|---:|---:|
| 음식점 지역 | 178.78ms | 68.97ms | -61.4% | +30.0% |
| 음식점 키워드 | 266.93ms | 74.40ms | -72.1% | +212.9% |
| 음식점 복합 필터 | 220.41ms | 76.39ms | -65.3% | +114.9% |
| 음식점 거리 | 205.74ms | 74.23ms | -63.9% | +45.3% |
| 숙소 키워드 | 293.77ms | 81.43ms | -72.3% | +129.3% |
| 희소 숙소 검색 | 339.34ms | 24.65ms | -92.7% | +1,051.6% |

RDB와 Elasticsearch는 같은 시나리오, 데이터 생성 규칙, 워밍업 수, 요청 수, 동시성, 반복 횟수로 측정했다. 다만 두 엔진의 내부 동작은 다르므로 이 결과는 검색 구현 전체의 체감 비용 비교이며 저장소 자체만의 순수 실행시간 비교는 아니다.

## 색인 시간

검색 측정 전에 RDB 데이터를 읽어 새 버전 색인을 만들고 alias를 교체했다.

| 데이터 | 색인 문서 수 | 초기 색인 시간 중앙값 |
|---|---:|---:|
| 도메인별 1,000건 | 2,000건 | 1,318.60ms |
| 도메인별 5,000건 | 10,000건 | 1,871.03ms |

이 값은 초기 전체 색인 시간이며 검색 응답시간에는 포함되지 않는다.

## 해석과 한계

- 데이터가 고정 규칙으로 생성돼 실제 운영 데이터의 단어 분포와 중복도를 완전히 반영하지 못함
- 로컬 단일 Elasticsearch 노드 결과이므로 운영 네트워크와 다중 노드 구성에서 재측정 필요
- BM25 검색 품질은 별도의 정답 데이터 기반 평가 필요
- 현재 거리 점수는 직선거리이며 도로 거리·이동시간 미반영
- AI 파싱과 서비스 간 HTTP 왕복을 포함한 전체 응답시간 측정 필요
