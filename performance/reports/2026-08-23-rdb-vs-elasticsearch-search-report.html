RDB와 Elasticsearch,
검색 결과와 성능은 어떻게 달랐나

Gangwon Companion 검색엔진 비교 보고서 · 여행지 개요(destination_details.overview) 검색 반영

한 줄 결론. 일반적인 지역·메뉴 검색에서는 현재 규모의 RDB도 충분히 빠르지만, 긴 여행지 개요를 대상으로 한 키워드 검색은 Elasticsearch가 크게 유리했다. 대표 시나리오인 바다 산책의 p95는 RDB 763.519ms, ES 27.944ms로 ES가 약 27.3배 빨랐다. 다만 평균 결과 Jaccard가 0.3542이므로 속도만으로 전환을 결정해서는 안 된다.

데이터와 동일성

  • PostgreSQL public 스키마의 실제 수집 데이터 사용
  • 같은 RDB aggregate 전체를 새 ES 인덱스로 재색인
  • 재색인 전후 source/indexed 문서 수 일치 확인 후 alias 교체
  • 두 엔진에 같은 HTTP 요청과 같은 결과 제한을 적용

합성 데이터 1,000/5,000건 벤치마크도 별도 문서에 있지만, 이 보고서의 핵심 비교 수치는 실제 수집 데이터로 수행한 최신 live 결과만 사용했다.

3. 두 검색 방식의 차이

PostgreSQL RDB 검색

JPA Specification으로 조건을 동적으로 만들고, 각 검색어를 대상 컬럼의 lower(field) LIKE '%term%'와 비교한다. 여행지 개요는 destination_details에 대한 상관 EXISTS 서브쿼리로 확인한다.

검색 대상
여행지: 이름·주소·개요 / 음식점: 이름·메뉴·주소 / 숙소: 이름·설명·주소

  • 장점: 별도 검색 인프라 없이 원본 데이터가 즉시 반영되고 트랜잭션 일관성이 단순하다.
  • 장점: 지역·정형 조건과 현재 소규모 데이터에서는 응답이 빠르다.
  • 단점: 선행 와일드카드와 긴 텍스트의 상관 서브쿼리는 일반 B-tree를 활용하기 어렵다.
  • 단점: 형태소, 동의어, 필드 가중치와 관련도 튜닝이 제한적이다.

Elasticsearch BM25 검색

RDB 데이터를 문서로 펼쳐 searchText에 이름·주소·테마·개요 등을 합친 뒤 역색인한다. multi_match/cross_fields로 검색하며 이름 정확 일치와 구문 일치에 추가 가중치를 준다.

검색 규칙
name^5, searchText^2, 주소 검색 / 처음에는 AND / 0건이면 OR + 최소 70% 토큰 일치

  • 장점: 긴 전문 검색, BM25 순위화, 한국어 분석과 가중치 확장에 적합하다.
  • 장점: 검색량과 문서 수 증가에 수평 확장이 쉽다.
  • 단점: 재색인·alias·동기화 지연·장애 복구 등 운영 요소가 늘어난다.
  • 단점: 색인 설계와 분석기 설정에 따라 결과 관련도가 크게 달라진다.
공통 동작: 지역·도메인·거리·hard filter를 적용하고, 최초 검색이 0건이면 검색어 토큰의 70% 이상이 맞는 완화 검색을 한 번 수행한다. 최종 후보는 점수 내림차순, 동일 점수는 placeId 오름차순으로 정렬한다.

5. 검색 예시 하나: “강릉에서 바다 산책”

AI 입력 파서가 자연어에서 장소 유형, 지역, 검색어를 추출했다고 가정한다. 검색엔진에 전달된 실제 비교 시나리오는 다음과 같다.

{
  "domain": "DESTINATION",
  "slot": "D1_DESTINATION",
  "region_codes": ["GANGNEUNG"],
  "query_text": "바다 산책",
  "limit": 10
}

RDB가 검색한 과정

  1. 강릉의 TourAPI 시군구 코드로 후보를 제한한다.
  2. 바다, 산책을 공백 기준으로 나눈다.
  3. 각 단어가 여행지 이름·주소 또는 상세 개요에 포함되는지 LIKE와 상관 EXISTS로 확인한다.
  4. 두 단어를 모두 만족한 후보를 점수와 ID로 정렬해 10건을 반환한다.

결과: p95 763.519ms · 10건

ES가 검색한 과정

  1. domain=DESTINATION, regionCode=GANGNEUNG을 filter context로 제한한다.
  2. 미리 역색인한 이름·주소·테마·개요에서 두 토큰을 AND로 검색한다.
  3. 이름 정확 일치·구문 일치와 BM25 관련도 점수를 반영한다.
  4. 점수와 ID로 정렬해 10건을 반환한다.

결과: p95 27.944ms · 10건

두 엔진에서 공통으로 나온 결과는 7건이고, 합집합 대비 교집합인 Jaccard는 0.5385였다. 같은 순위에 같은 장소가 놓인 위치는 3개뿐이었다. 따라서 ES가 약 27.3배 빨랐다는 사실과 별개로, 어느 결과가 사용자 의도에 더 맞는지는 사람이 후보를 판정해야 한다.

순위와 ID는 원본 측정 JSON의 result_ids, 장소명은 동일한 실데이터 PostgreSQL의 destinations 테이블에서 조회했다. 재현성을 높이려면 다음 측정부터 place_id와 name을 결과 파일에 함께 저장하는 것이 좋다.

6. 결과를 읽을 때 주의할 점

검색 계약 불일치: 반려동물·휠체어 값이 NULL일 때 RDB는 후보를 INSUFFICIENT_EVIDENCE 상태로 유지하지만 ES는 true 문서만 통과시킨다. 그래서 일부 정책 시나리오는 RDB 5건, ES 0건이다. 이는 엔진 속도나 품질 우열이 아니라 구현 규칙이 서로 다른 문제다.
  • 평균 Jaccard 0.3542, 완전한 순서 일치 5/20이므로 현재 결과는 성능 비교와 계약 차이 발견에 의미가 있다.
  • 결과 관련성의 승자를 정하려면 검색어별 사람 판정(예: 0~3점)과 NDCG@10, Recall@10 측정이 필요하다.
  • 이번 실데이터 측정은 시나리오당 30회 순차 요청이다. 운영 결론 전 동시성 1·10·50, 300회, 3회 반복이 필요하다.
  • ES 초기 색인 시간은 검색 응답시간에 포함되지 않는다. PostgreSQL을 원본으로 유지한다면 CDC·재색인·alias 롤백 전략도 비용에 포함해야 한다.

7. 결론

지역·정형 필터 중심이고 데이터가 현재 수준이라면 RDB는 단순하고 충분히 빠른 선택이다. 반면 여행지 개요처럼 긴 텍스트를 탐색하고 향후 형태소·동의어·필드 가중치·고동시성을 확장하려면 Elasticsearch가 더 적합하다.

다음 의사결정 순서는 ① 두 엔진의 NULL 정책 계약 통일, ② 동일 데이터 재색인, ③ 사람 판정 검색 정답 세트 평가, ④ 운영 예상 동시성 부하 측정이다. 이 네 조건을 맞춘 뒤 속도와 관련도를 함께 보고 운영 엔진을 확정하는 것이 안전하다.
